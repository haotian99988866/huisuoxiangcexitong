# 会所信息展示与 Telegram 频道机器人

本项目包含 React/Vite 前端、Flask API、Telegram 频道机器人和 MySQL 数据库，用于展示会所资料、服务项目及技师信息，并从指定频道接收带标签的图片来更新会所封面。


## 项目结构

```text
.
├── bot/
│   ├── api_server.py          # Flask API，生产运行使用 Waitress
│   ├── main.py                # Telegram 频道照片监听机器人
```

## 当前功能

- Telegram资料页的功能介绍与短简介维护于 `bot/bot_profile.py`，按三行分组展示出勤、外送、影视音乐、资讯、会员及话费服务，不使用逐项图标或命令列表，并注明充值订单人工处理。介绍保持180个UTF-16单元以内（Telegram上限512字符），短简介不超过120字符；与 `/start` 欢迎信息独立。调整后须通过Telegram Bot API同步到机器人资料页，单纯重启主机器人不会更新。
- `/start` 欢迎信息与使用指南维护于 `bot/welcome.py`，不再介绍已下架的水墨与今日时令。主菜单在简短说明下直接展示全部17个功能按钮，包括会所/外送、影音娱乐、资讯与提醒、充值服务、我的与客服；账户和订单需在 Telegram 小程序内操作。新闻和出勤订阅入口在原消息中打开，并提供返回主菜单按钮；个人分享归属及旧分类消息兼容均保留。改动须重启主机器人；已有欢迎消息不会自动改写，发送 `/start` 获取新菜单。
- 主菜单使用消息内联按钮，不再常驻显示输入框下方的大量功能键。`/start` 和新菜单回复会移除旧版回复键盘；旧文字按钮在更新前仍可兼容响应。发送私聊指令时，机器人会删除此前登记的菜单／功能提示消息；处理 `/start` 后也会删除该条用户指令。无法删除的消息会记录日志；机器人不扫描或删除未登记的历史消息、其他用户留言、订单通知或新闻提醒。
- 新闻和出勤入口只打开现有订阅管理，不会自动订阅；余额、订单、收藏和人员订阅等需认证功能仍须从 Telegram 打开小程序，不传用户ID或绕过现有认证。分享按点击者生成专属邀请链接。频道和联系入口仍使用固定的本站中转地址，不接受任意目标网址。
- Telegram会员和话费代充余额充足时沿用原扣款与人工办理流程；余额不足时建立独立的待联系申请，不扣余额、不计入已付款订单。申请通过机器人私聊发送给客人和负责人，负责人直接回复申请消息即可经机器人联系客人；重试沿用同一申请编号。
- 会所列表、搜索标签、封面图片展示。
- 会所服务项目和技师工号展示。
- 每个服务项目可配置其适用技师；点击项目展开技师工号，点击工号查看已确认照片。
- “名玺水汇会所”频道公告按牌号解析当日技师，并从公告中提取三通、潮喷、SM、双仪等服务分类；技师照片按数字工号自动匹配。
- “凯迪/大浪淘沙会所”按价目表展示牌位、车模、日韩类别及已确认关联的技师工号，不依赖出勤公告。
- “大西洋/五象会所”按最新价目表展示至尊、佳丽、车模、皇贵妃、皇后、1牌、3牌、0牌、豹子及日韩类别的价格（不展示原价或预约价），服务时长90分钟；技师照片需能识别唯一类别和工号后才会自动归类。
- “帝豪会所”按频道价目表展示0牌、1牌、2牌、6牌艺人、7牌公主、8牌佳丽和9牌贵妃的活动价；工号可按明确类别标签或牌号前缀归类，仅展示OCR确认年满18岁的照片资料。
- 各会所出勤板块显示频道最近一条消息的时间；从机器人监听到消息后开始记录，不回溯历史频道消息。
- 技师详情会从照片 OCR 提取工号、年龄、身高、胸围、体重、籍贯和籍贯字段后的服务介绍；未识别出的资料不会补猜。
- 会所详情和技师列表 API。
- Telegram 机器人监听配置中的 10 个频道；带有对应主标签的图片会写入 `venue_photos`，并更新会所封面。
- 机器人在本地 OCR 频道照片中的纯数字工号；唯一、高置信度且属于当日出勤名单的照片会自动关联，其他照片待人工核对。
- 匹配时忽略工号的前导零（例如照片上的 `21` 可匹配出勤名单中的 `021`）；如名单中同时存在两种写法，则保留人工核对。
- 前端可点击今日工号查看已自动匹配或人工确认的照片；待核对照片不会通过公开 API 展示。
- 数据存储使用 MySQL，默认数据库名为 `venue_db`。

### 当前数据模型

- `venues`：会所资料；`technician_codes` 存放逗号分隔的技师工号。
- `venue_photos`：频道图片及消息记录。
- `technicians`：独立技师记录。
- `service_items`：会所服务项目及价格。
- `service_item_technicians`：服务项目与可服务技师工号的多对多关联。
- `technician_photos`：照片 OCR 结果、出勤日期、候选工号及审核状态；Telegram `file_id` 只由后端使用。
- `attendance_groups`：保存“名玺水汇会所”按牌号和服务分类解析出的每日技师列表。

前端“今日出勤”数量目前根据 `technician_codes` 计算；技师团队列表则读取 `technicians` 表，两者是不同数据来源。当前数据库没有会所介绍字段，因此详情 API 暂时返回空介绍。

## 本地开发（Windows）

### 准备环境变量

在 `bot/.env` 配置以下变量。不要将实际令牌或密码提交到 Git：

```env
TELEGRAM_BOT_TOKEN=替换为机器人令牌
DB_HOST=127.0.0.1
DB_PORT=3306
DB_USER=应用专用数据库用户
DB_PASSWORD=数据库密码
DB_NAME=venue_db

# 可选：跨域来源，仅在前后端不同源部署时配置
CORS_ORIGINS=https://你的前端域名

# 可选：API 监听配置；本机反向代理部署通常保持默认值
API_HOST=127.0.0.1
API_PORT=8000
```

确保 MySQL 服务正在运行，并已创建数据库及所需表。机器人和 API 共享 `bot/.env` 中的 MySQL 配置。

应用技师照片表迁移（在仓库根目录执行）：

```powershell
Get-Content -Raw .\bot\migrations\002_technician_photos.sql | mysql -u root -p venue_db
Get-Content -Raw .\bot\migrations\003_technician_photo_ocr_error.sql | mysql -u root -p venue_db
Get-Content -Raw .\bot\migrations\004_service_item_technicians.sql | mysql -u root -p venue_db
Get-Content -Raw .\bot\migrations\005_service_item_technician_duty_date.sql | mysql -u root -p venue_db
Get-Content -Raw .\bot\migrations\006_attendance_groups.sql | mysql -u root -p venue_db
Get-Content -Raw .\bot\migrations\007_venue_channel_activity.sql | mysql -u root -p venue_db
Get-Content -Raw .\bot\migrations\008_ktv_room_videos.sql | mysql -u root -p venue_db
Get-Content -Raw .\bot\migrations\009_delivery_media.sql | mysql -u root -p venue_db
Get-Content -Raw .\bot\migrations\010_delivery_media_age.sql | mysql -u root -p venue_db
# 给已入库的旧外送照片补识别年龄（OCR）
bot\venv\Scripts\python.exe bot\backfill_delivery_age.py
```

Telegram 出勤公告的固定分区会自动同步到该日期对应的服务项目：小项、中项、高项、中医按摩、修脚师分区中的工号会关联到同类别下的项目，且只在公告日期显示。公告中的分区名单视为该类别下所有项目均可服务；重复收到同日期公告时会更新当日对应关系。

若需手动调整某天的名单，先查出该会所服务项目 ID，再为项目插入可服务的工号：

```sql
SELECT id, name FROM service_items WHERE venue_id = 1 ORDER BY sort_order, id;

INSERT INTO service_item_technicians (service_item_id, duty_date, technician_code)
VALUES (13, '2026-10-23', '098'), (13, '2026-10-23', '021');
```

替换示例中的服务项目 ID、日期和工号为实际名单。网页点击项目名称即可展开当日工号，点击工号可查看已确认照片。

## API

所有请求均为 `POST /webhook`，请求和响应使用 JSON。

| `action` | 请求字段 | 返回内容 |
|---|---|---|
| `get_venues` | 无 | `{ "venues": [...] }`，包含服务项目及技师工号 |
| `get_venue_detail` | `id` | 会所详情 |
| `get_technicians` | `venue_id` | `{ "list": [...] }` |

本地调用示例：

```powershell
$body = @{ action = "get_venues" } | ConvertTo-Json
Invoke-RestMethod `
  -Uri "http://127.0.0.1:8000/webhook" `
  -Method Post `
  -ContentType "application/json" `
  -Body $body
```

## 服务器部署要点

1. 在服务器安装 Python、Node.js 和 MySQL；创建数据库及表，并配置 `bot/.env`。为应用创建权限受限的数据库账号，不要在服务器上使用 MySQL `root` 账号运行应用。
2. 安装后端依赖：`python -m pip install -r requirements.txt`。
3. 使用进程管理器运行 `python api_server.py` 和 `python main.py`，并配置服务异常重启及日志管理。
4. 由 Nginx/Caddy 提供 HTTPS 和静态前端文件，并将 `/api/` 反向代理到 `http://127.0.0.1:8000/`。前端需要配置 SPA 路由回退到 `index.html`。
5. 默认 API 仅监听本机回环地址，适用于同机反向代理。若必须跨主机访问，才将 `API_HOST` 配为 `0.0.0.0`，并通过防火墙限制来源。
6. 前后端同域部署时通常不需要放宽 CORS；分域部署时，将精确的前端 HTTPS 来源填入 `CORS_ORIGINS`。
7. `VITE_API_BASE_URL` 是前端构建时变量；同域部署使用默认 `/api`，分域部署时在构建前设置为完整 API 前缀，例如 `https://api.example.com`。

本机管理台调试（默认关闭）：只在本机 API 进程设置 `LOCAL_ADMIN_DEBUG=1`，前端构建或开发进程设置 `VITE_LOCAL_ADMIN_DEBUG=1`。仅支持通过 `http://localhost:4173`、`http://127.0.0.1:4173` 或对应的 `5173` 端口访问；API 必须绑定回环地址。调试请求必须来自本机且带本地来源，不接受转发、隧道或租户请求；Vite 代理也会移除非本机来源的调试请求头。已有 Telegram 身份仍按正常权限验证。调试写入会使用审计账号 `-1`，并真实修改当前数据库；不要用于实际充值或客户数据操作。结束后取消两个环境变量并重启 API、重新构建前端；线上不要设置这些开关。

> 当前 API 未实现登录或访问令牌校验。不要在未增加访问控制和限流的情况下，将 API 直接暴露到公网。

## 数据库和机器人注意事项

- 外送人员档案上线前应用 `bot/migrations/011_delivery_people.sql`。机器人和 API 启动时也会补建档案/审计表，并将现有相册拆分为每张不同照片一个档案；同会所 dHash 距离不超过 4 的重复/近似照片归入同一档案。该历史数据调整只在首次升级时执行。新视频在相册只有一张不同照片时关联该档案，否则单独建档。
- 外送人员管理页复用会所的照片网格和详情弹窗：列表懒加载照片缩略图，纯视频档案显示文字封面；点击档案后才挂载详情媒体，视频点击播放后才加载，关闭弹窗即卸载。统一显示档案编号，不再显示名称输入、相似档案或授权操作。
- 会所和外送统一从管理台“人员”的“选择会所”下拉框直接进入人员档案，不再显示“人员概览/档案维护”切换页签；会所保留档案换人，详情可添加说明、确认提交及删除档案，不提供文件上传；外送保留说明、补充媒体和删除功能。原会所概览的内部标签和出勤订阅不再提供此页面入口，已有记录不删除。
- 会所说明仅后台管理员可见，最多2000字，保存使用版本检查避免覆盖他人修改。删除需二次确认，后台与客人端列表、详情和档案照片入口均隐藏，停止该档案出勤提醒，但保留频道消息、历史出勤和原媒体关联；重启或频道重发不会自动恢复，删除不代表工号换人。说明清除，操作记录审计。应用 `014_staff_archive_management.sql`（启动也会检查补建，已自动补建时不要重复执行 ALTER）。
- 会所客人出勤订阅开放所有支持档案的会所（1、2、4、5、6），公开有效档案均可订阅，不再依赖旧的逐人客人授权或内部标签；原授权记录保留但不再作为个人订阅开关。卡片和详情入口同步，未发布当前班次出勤时可订阅，持续到取消；白班06:00–18:00、晚班18:00–次日06:00各最多提醒一次，只提醒订阅后的新发布，不补发历史。1、2按当前班次最新出勤名单，4、5、6另结合本班次频道档案照片；名单移除、取消、删除、屏蔽、工号换人及帝豪未确认成年均在发送前重新核对，订阅不转移给新人。沿用已有订阅表、Telegram主入口身份验证、原请求编号重试和发送不明不重发策略；后台管理和租户展示不提供个人订阅操作。
- 外送档案详情按“照片/视频 → 媒体数量及更新时间 → 说明与添加媒体”的顺序展示，删除档案按钮位于顶部固定区域右侧，以红色文字与底部提交操作分开，保留二次确认。
- 外送后台档案复用会所班次窗口（本机时间18:00–次日06:00）：该档案关联的频道照片在本班发布即标记“今晚出勤”，按同一外送会所内相同/近似照片匹配；不同照片不按人脸或工号自动认人。本班无照片显示“本班未见照片”（不代表实际缺勤），白班显示“外送仅晚班”。视频、后台上传和说明修改不触发出勤；已删除档案不计数。列表在未打开详情时每60秒更新，编辑不被刷新打断。
- 外送档案编辑使用固定底部“取消修改 / 确认并提交”操作栏；提交前核对说明和待上传文件，说明与新媒体在同一数据库事务中保存，失败回滚，未提交关闭需确认。删除按钮仍独立即时确认执行，不属于待提交修改。
- 外送补充媒体和说明使用 `bot/migrations/012_delivery_person_attachments.sql`（API 启动也会自动建表）。说明最多2000字符；每次上传一个 JPG/PNG/WebP 照片（最多5MB）或 MP4/WebM 视频（最多20MB）。服务端验证文件内容，照片转换为 JPEG；补充媒体保存在 MySQL 的独立表，同一档案相同文件重复上传不会增加记录。说明和补充媒体仅后台保存，不发频道、不进入客人端，也不参与频道照片建档去重。读取补充媒体必须验证管理员身份；调试模式仍仅限本机。数据库 `max_allowed_packet` 和部署代理的请求体限制需允许21MB以上，备份时应包含这两张新表。
- 客人端外送默认沿用“最新上新”，右上角提供“人员档案 / 晚班出勤”切换，不同时堆叠展示。档案页按当前外送分类显示历史有效、已授权档案及今晚出勤标签，仅返回通过原有成年过滤的频道媒体；后台说明、补充媒体和管理操作不公开。小苹果/红苹果沿用频道分类规则，未知类别两边可见；租户仍受会所范围限制。
- 外送重复照片去重不隐藏原档案成年相册的视频；仅照片出勤发布匹配到原档案时，人员档案和晚班出勤详情均可查看该档案的历史公开视频。补充媒体仍不公开，未通过成年过滤或不属于当前苹果分类的视频不补入；涉及多个人员档案的相册不自动混合历史媒体。
