# 项目结构规范（房规 v1）

> 适用范围：**以后所有新项目**都照这个结构建，不再逐个商量。
> 本规范以 `country-agent` 的结构为基线，补上三个"吃过亏才知道要加"的配置。
> 文章最后给出「综合管理后台」的逐项落位，证明这套结构不用改就能用。
>
> **命名说明**：文中的 `<project>/` 是**单个业务项目目录名的占位符**
> （例如 `mingxi-shuihui/`、`mingxi-admin/`、`country-agent/`），
> **不是**工作区总目录 `D:\project`。总目录只放各项目文件夹与 `_规范` 等公共物。

## 1. 标准目录树

```text
<project>/          ← 例：mingxi-shuihui/   （≠ D:\project）
├── .github/
│   ├── copilot-instructions.md          # 全局宪法，每个请求都加载
│   └── instructions/

│       ├── backend.instructions.md      # applyTo: "backend/**/*.py"
│       └── review.instructions.md       # applyTo: "**"（收尾自审）
```

## 2. 每个目录的边界（放什么 / 不放什么）

| 目录 | 放什么 | 不许放 |
|---|---|---|
| `core/` | 配置、异常、日志、公共依赖、密码与安全工具 | 业务逻辑、SQL |
| `db/schema.py` | 幂等建表、补列 | 业务判断 |
| `db/models/` | 行结构（数据类等） | ORM 基类、查询业务 |
| `schemas/` | Pydantic 入参出参，与契约字段一一对应 | 业务判断、DB 访问 |
| `routers/` | 收参 → 调 service → 返回（三步内） | 业务分支、直接查库、try/except 拼响应 |
| `services/` | 全部业务逻辑、校验、外部调用 | HTTP 对象（Response/HTTPException） |
| `api/client.ts` | 统一请求、错误码 → 文案 | 具体页面的业务 |
| `pages/*/index.tsx` | 布局标签、公共组件、从 hooks 解构的数据 | fetch、校验、状态机 |
| `pages/*/hooks.ts` | 该页全部逻辑 | JSX |
| `components/ui/` | 无业务语义的基础件 | import `pages/` 或 `api/` |
| `locales/` | 所有用户可见文案 | 组件内硬编码中英文 |

## 3. 强制命名与写法约定

| 项 | 约定 |
|---|---|
| Python 文件 | 小写下划线；一个领域一个文件（`country.py`） |
| 前端组件目录 | PascalCase（`CountryDetail/`），文件名同组件 |
| 导出方式 | 全命名导出，**禁止 default export** |
| 表结构变更 | 写进 `db/schema.py` 的幂等逻辑；缺列用 `ALTER TABLE … ADD COLUMN` |
| 错误 code | 大写下划线（`COUNTRY_NOT_FOUND`），在 `core/exceptions.py` 与契约同时枚举 |
| 环境变量 | 后端 `APP_*`，前端 `VITE_*` |
| CSS 类名 | 页面 `.page-<name>` 前缀；组件 `.block__element` |
| 端口 | 前端 51xx，后端 80xx，同一项目内错开 |

## 4. 三条不可协商的落地检查

1. `frontend/src/api/types.ts` 必须是生成物。CI/本地检查：重新生成后 `git diff --exit-code`。
2. 空库上跑一次 `ensure_database()`（或等价建表）必须能起服务；SQL 全部参数化。
3. 每一层的 `index.tsx` 里出现 `fetch` 即视为违规。
4. `pyproject.toml` 默认不含 `sqlalchemy` / `alembic`（例外见《默认技术栈.md》）。

## 5. 建议补充的三个目录（基于真实踩坑，建议纳入房规）

基线结构解决的是"应用层"，但项目落地还有三样东西每次都要临时决定，建议一次定死：

### 5.1 `deploy/` —— 部署物

```text
deploy/
├── <project>.service        # systemd 单元（Linux）或
├── start-tunnel.ps1         # Windows 下把服务拉起来
├── cloudflared/             # 隧道配置与凭证
└── Caddyfile                # 反向代理
```

**为什么加**：名玺水汇这个项目里，隧道配置、凭证、上线脚本没地方放，散在根目录，后来才收敛。

### 5.2 `tools/` —— 一次性/运维脚本

```text
tools/
├── scan-media.ps1           # 扫描素材生成清单
└── fix-dns.cmd              # 环境修复
```

**为什么加**：这类脚本不属于业务，放 `backend/src` 会污染代码结构，放根目录会越来越乱。

### 5.3 `docs/status.md` —— 进度交接

**为什么加**：规则文件描述"规则"，`status.md` 描述"进度"。没有它，新会话（或换人）必须先问一遍"做到哪了"。

### 5.4 启动脚本放根目录

```text
<project>/
├── dev.cmd         # 开发：起前后端热更新
├── serve.cmd       # 前台调试
└── online.cmd      # 一键上线（构建→建表→起服务→起隧道）
```

**为什么加**：非技术用户不会敲长命令，双击是唯一可用的人机界面。

## 6. Windows 环境的两条硬规则（血泪教训）

1. **`.ps1` 必须存成 UTF-8 with BOM**。PowerShell 5.1 会把无 BOM 的 UTF-8 当 ANSI 读，中文注释直接导致语法错误、整个服务起不来。
2. **`.cmd` 文件注释只用 ASCII**。同上，编码问题会让批处理解析出错。

> 这两条不属于"结构"，但每次新项目都会踩，写进房规比写在某个项目的文档里更有用。

---

## 7. 单语项目的例外

结构里默认有 `locales/zh` + `locales/en`。若项目确定只做中文：

- **允许**只建 `locales/zh/`，`app/i18n.ts` 可省；
- **但不允许**在组件里硬编码文案——仍要走文案表，否则以后加英文要全量重写。

## 8. 这套结构用在「综合管理后台」上

**结论：0 个新增顶层目录**。原来我提的 `modules/site/adapters/` 是多余的——标准里的 `services/external_api.py` 就是"外部数据源客户端"，后台访问官网数据属于同一类。

| 后台需求 | 落在标准里的位置 |
|---|---|
| 登录、密码哈希、会话 | `core/security.py` + `core/deps.py` |
| 登录/会话/锁定业务 | `services/auth.py` |
| 审计记录 | `db/models/audit.py` + `services/audit.py` |
| 读官网询盘、改状态 | `services/site_db.py` |
| 读写官网内容 JSON | `services/site_content.py` |
| 媒体上传与清单 | `services/site_media.py` |
| 接口 | `routers/auth.py`、`dashboard.py`、`inquiries.py`、`content.py`、`media.py` |
| 入参出参 | `schemas/auth.py`、`inquiries.py`、`content.py`、`media.py` |
| 布局 | `layouts/AdminLayout/` |
| 页面 | `pages/Login/`、`Dashboard/`、`Inquiries/`、`Content/`、`Media/` |
| 部署 | `deploy/cloudflared/`、`deploy/Caddyfile` |
| 启停 | 根目录 `dev.cmd`、`online.cmd` |

### 「综合」怎么体现（不加模块目录）

系统名叫「综合」，将来要管会所，但**不加 `modules/` 层**，用命名前缀隔离：

| 项目 | service | router | schema |
|---|---|---|---|
| 官网（V1） | `services/site_*.py` | `routers/{dashboard,inquiries,content,media}.py` | `schemas/*.py` |
| 会所（V2） | `services/club_*.py` | `routers/club_*.py` | `schemas/club_*.py` |

规则：**跨项目的代码不互相 import**，只通过各自 service 暴露的函数调用。

### 什么时候该重新考虑加一层

当 `routers/` 超过 **25 个文件**，或出现第二个项目模块时，再考虑引入 `modules/` 分组——**现在不做**，符合"不提前抽象"。
