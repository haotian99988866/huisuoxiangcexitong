# 请求规范 · 你怎么提需求，我才能准确理解

> 目的：把**沟通**也变成有规范的东西，减少来回猜。
> 本文是给你用的，不是给我用的。照着填，基本不会跑偏。

---

## 1. 一个模板，五个空

不需要长篇大论，填满这五行就够：

```
【做什么】一句话，动词开头
【在哪】  项目 / 页面 / 文件（只写你确定的）
【别动】  这次不希望我碰的东西
【算完成】怎么验证它成了（可看、可点、可跑）
【待定】  你还没想好的点，明确说出来
```

### 填好的例子

```
【做什么】询盘列表加一个「按项目筛选」的下拉
【在哪】  综合管理后台 → 询盘页
【别动】  询盘表结构、现有筛选
【算完成】选 KTV 只剩 ktv 的询盘；选全部恢复；URL 带筛选参数
【待定】  手机号要不要跟着筛选变？没想好
```

## 2. 三档：不是每个需求都要写五行

| 档位 | 什么时候用 | 怎么写 |
|---|---|---|
| **一句话档** | 改文案、调颜色、换图片、改个数字 | 直接说，不用模板 |
| **三行档** | 加个小功能、改个交互 | 做什么 / 算完成 / 别动 |
| **完整档** | 跨多个文件、动接口、动数据库、新项目 | 用上面五行模板；新项目再加「技术栈」一行 |

**判断标准**：如果你自己都说不清「算完成」长什么样，就直接用完整档——那个空往往是误解的源头。

---

## 3. 三句话能省掉一半来回

提需求时，先自问这三个：

1. **我要的最终画面是什么？**（不是"加个按钮"，是"点了之后会怎样"）
2. **怎么算成了？**（我能看到什么、点到什么）
3. **什么不能动？**（数据库、现有页面、别人的项目）

---

## 4. 我们真实对话里的反例 → 正例

这些是本次对话中确实绕了路的，对照看最直观。

### 反例 1：范围不清

> ❌「帮我全部执行吧」

我当时的困境：不确定「全部」包含哪些，也不确定你允许我改什么。

> ✅「把剩下三件都做完：① 删两条误建记录 ② 开 HTTPS 强制跳转 ③ 换真实联系方式（电话 X，地址 Y）。前两件你选做法，第三件用我给的信息。」

### 反例 2：指代不明

> ❌「这个项目它可以」

我花了三轮才确认：你说的是 `huisuoxiangcexitong` 能访问，用来对比新域名为什么不行。

> ✅「huisuoxiangcexitong（app.haotianzhushou.com）能打开，mingxispa.com 打不开——帮我查两者解析差在哪。」

### 反例 3：只说要什么，没说边界

> ❌「改成和老项目一致」

「一致」指什么？目录？启动方式？还是代码风格？我猜了启动方式。

> ✅「把启动方式改成和老项目一致：隐藏窗口、日志落盘、重复启动不叠加。代码风格不用动。」

### 反例 4：需求里塞了多个动作

> ❌「后台系统的管理名称改成综合管理后台，还有约束规则我们还需要继续讨论」

第一件事是改代码，第二件是讨论。混在一句里，容易让我只做了一半。

> ✅ 拆成两条：
> - 「把系统名改成『综合管理后台』（文档 + 代码里的 app_name）」
> - 「约束规则先讨论，别改代码」

### 反例 5：名词没有共同定义

> ❌「对接完成后在开始」

「对接」我理解为：域名解析、内容填充、第三方接入、数据迁移……四种可能。

> ✅「等我把官网的电话地址图片填完（对接完成），你再开始后台。」

## 5. 高频场景速查

| 你想做 | 这样说 |
|---|---|
| 改文案 | 「首页副标题改成 xxx」 |
| 改样式 | 「卡片圆角从 8 改到 12，其他别动」 |
| 加字段 | 「询盘加一个『来源渠道』字段，下拉选，可空」+ 表结构怎么补 |
| 加页面 | 「后台加一个『员工』页：列表 + 新增 + 编辑，字段 a/b/c」 |
| 新项目 | 「新建 X；技术栈按 `_规范/默认技术栈`」或「例外：用 Y，因为 Z」 |
| 修 bug | 见第 6 节 |
| 重构 | 「把 X 拆成 Y 和 Z，行为不能变，改完跑现有测试」 |
| 查问题 | 「X 打不开，现象是……，我试过……，帮我定位」 |
| 暂停 | 「先停，已完成的不动，等我确认」 |
| 验收 | 「给我看改了什么 + 怎么验证 + 没做什么」 |

### 新建项目补一行

完整档在五行之外加：

```
【技术栈】按默认   ← 或：例外用 SQLAlchemy，因为要接已有 ORM 库
```

没写这一行时，按 `_规范/默认技术栈.md` 做（朴素驱动、不上 ORM）。
有页面时默认还要遵守 `_规范/前端移动与Telegram壳.md`（手机 / Telegram 壳 / 统一按钮封装）；官网不做底栏等例外须在需求里写明。

## 6. 报 bug 的三段式

```
【现象】哪个页面/操作，看到什么（错误文案照抄）
【复现】我做了什么 → 应该发生什么 → 实际发生什么
【范围】只有这个页面吗？换个设备/浏览器呢？
```

有截图最好，截图里包含地址栏。

## 7. 我会怎么回应（你可以据此要求我）

| 情况 | 我的行为 |
|---|---|
| 需求清楚 | 直接做，做完给「改了什么 + 怎么验证 + 没做什么」 |
| 有歧义 | **先问，不猜**。猜了会显式标注「假设：……」 |
| 跨 3 个文件 / 动契约 / 动表结构 / 删数据 | **先给方案，等你确认再动手** |
| 新项目要偏离默认技术栈 | **先确认例外与原因，再加依赖** |
| 你说「全部执行」 | 我会先列清单让你确认，不自己扩大范围 |
| 做完了 | 附验证输出，不只说「已通过」 |
| 没做某件 | 明确说「没做 X，因为 Y」，避免你以为漏了 |

---

## 8. 一句话总结

**「做什么 / 怎么算成 / 别动什么」——这三点说清，基本不会错。**

其余的（实现方式、文件怎么组织、用哪个库）你可以完全不管，那是我的事。
